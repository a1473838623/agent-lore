# agent-lore

> **让 AI 编码工具从人类的修正里自动学习仓库规范。**
> 你改了它写的代码，那个 diff 就是它该学的东西。

零依赖 · Node ≥18 · MIT · 定位为 **harness 扩展层**，不是 agent，不替代任何工具。

设计文档见 [DESIGN.md](DESIGN.md)。

---

## 它解决什么

现有 AI 编码工具的规范**全靠人手写**（CLAUDE.md / Cursor Rules / Copilot Instructions），
写完就开始腐烂。而每天都在产生一个免费、真实、高质量的学习信号，却被完全丢弃：

> Agent 写了代码，你改了三处。**那三处就是它没学会的东西。**
> 下一次，它还会那样写。

agent-lore 采集这个信号，归因、去噪、累计、提炼成规范，再在下次编辑前带外注入回去。

## 两条学习路径

**① 冷启动 —— 从现有代码库直接归纳**（不必等修正累积）

成熟仓库的规范已经写在代码里了。等「AI 写错 → 人修正 → 累计 3 次」对一个几万文件的老仓库是最慢的路径。

```bash
lore bootstrap --path /path/to/repo --stat    # 先看统计
lore bootstrap --path /path/to/repo           # 出归纳提示词
```

🔑 **不喂全文，喂统计特征。** 规范体现在**频次对比**上 ——
「@Autowired 34 次 vs 构造器注入 162 次」比读 100 个文件更能说明这个仓库的偏好，
token 成本还差几个数量级。实测 33000 个 Java 文件的仓库，抽样 3000 个文件几秒出结果：

```
依赖注入   A=    34  B=   162   83% 偏向B      ← 构造器注入
日志拼接   A=    34  B=  1991   98% 偏向B      ← {} 占位符
异常      A=    13  B=   531   98% 偏向B      ← catch 里记日志
集合创建   A=  1136  B=   418   73% 偏向A      ← 未过 80% 线，不下结论
```

**倾向不明确（<80%）的维度不编规范** —— 混用往往是有意的（新老代码并存）。

**② 持续学习 —— 从人类修正中提炼**

```
Agent 写文件 ──► 快照
                   │
           人类随后修改             ← 免费、持续、外部信号
                   │  diff
          归因（三分类 + 置信度闸）
           ├─ feature 业务变更 → 丢弃
           ├─ bug     修 AI 的错 → 踩坑，绑定文件
           └─ style   规范修正   → 候选
                   │  同类累计 ≥3 次
             人工确认 → 入库
                   │
        convention → CLAUDE.md（常驻，不检索）
        pitfall    → 编辑前 hook 带外注入（≤300 token）
                   │
          度量：修正复发率           ← 闭环验证
```

两条路径的分工：**bootstrap 解决冷启动，修正学习负责持续校正**。
前者一次性拿到大部分规范，后者捕捉代码库演进和 bootstrap 归纳不出来的细节。

## 快速开始

```bash
git clone <repo> && cd agent-lore && npm link   # 或直接用 node bin/lore.js
```

```bash
lore init           # 一键装 Claude Code hook，并打印其它 harness 的接入片段
lore init --dry     # 只预览不写盘
lore dashboard      # 本地看板 http://127.0.0.1:4519
```

`lore init` 会**先备份** `~/.claude/settings.json`，且重复执行不会叠加配置。

### 三层接入

| 层 | 命令 | 适用 | 注入时机 |
|---|---|---|---|
| **L1** | `lore init` | Claude Code | **编辑前强制注入**，最完整 |
| **L2** | `lore mcp` | Cursor / Cline / Codex / Windsurf … | 靠 agent 主动调用 |
| **L3** | `lore watch` | **任何工具，包括没有扩展点的** | 只采集，不注入 |

L2/L3 的接入片段由 `lore init` 一并打印。**L3 是可移植性的兜底** ——
只要 agent 改了文件工作区就有变化，未经 L1/L2 上报的变更即视为人类修正，
这个推断在任何 harness 下都成立。

## 日常用法

**装上 hook 之后，采集是全自动的** —— `PostToolUse` 每次触发都会顺带扫描一遍，
人类的修改在下一次 agent 写文件时被自动捕获，不需要你记得敲 `lore scan`。

需要你参与的只有归因和确认：

```bash
lore review                # 输出归因提示词 → 交给当前 harness 的模型判断
lore learn --json '{...}'  # 回灌归因结果
lore promote               # 看达阈值的规范
lore promote --yes         # 人工确认入库          ← 这一步刻意保留人工
lore sync                  # 规范写进项目 CLAUDE.md
lore stats                 # 修正复发率
```

### 归因的单位是「一次交互」，不是「一个文件的 diff」

一次需求改动常横跨多个文件。若逐个文件归因：既是重复劳动，模型又缺跨文件上下文
——单看一个文件的 diff，常常判不出是 style 还是 feature。

所以按 `session_id` + agent 写入时间邻近性聚成**批次**（hook 事件给了 session_id，
但没给 turn id，用「同会话 + 间隔 < 3 分钟」近似一个 turn）。整批一次判断，
也可以「拆开」单独处理其中某个文件。

> 🔑 **一个批次只算一次证据，不是 N 次。**
> 一次交互里 agent 写了 5 个文件、人用同样方式改了 5 处，这是**一个人做的一个决定**。
> 按 N 次计，单次交互就能顶到确认阈值，"累计 ≥3 次才泛化"这道闸就形同虚设。
> （bug 类除外：踩坑绑定具体文件，批次内每个文件各记一条。）

### 需求边界按会话隔离

同一个仓库可能同时开多个会话做不同需求。若只存一份仓库级边界，
B 会话会被注入 A 的边界然后拒绝干活——而且这种串扰很隐蔽，表现为"agent 莫名其妙不肯改"。
所以边界按 `session_id` 存，取用时**本会话优先，退回仓库默认**。

### 人工介入到底有多少

采集全自动。归因**应该**自动（`lore auto`，或看板上的「全部自动归因」按钮），
手填只是没配 `ANTHROPIC_API_KEY` 时的降级路径。

入库分两档，绝大多数不需要你看：

| | 条件 | 处理 |
|---|---|---|
| **自动入库** | 累计 ≥5 次 **且** 归因平均置信度 ≥0.9 **且** 与已有规范无话题重叠 | ⚡ 直接进库 |
| **待确认** | 任一条不满足 | 列出**具体是哪条不满足**，交你判断 |

> 为什么保留这道闸：**代价不对称**。错规范入库后每次编辑都注入、污染所有后续代码，
> 而且不容易察觉；漏一条只是下次再学一遍。
> 但"每条都问"确实过头了，所以按置信度和累计次数分级 —— 真正需要人的只有边缘情况，
> 尤其是**与已有规范话题重叠**那种：是重复还是冲突，字符串相似度判不出来（实测区间完全重叠），
> 只能人看。

阈值都在 `src/config.js` 的 `TUNING.autoPromote` 里，可按 `lore stats` 的复发率反调。

有 `ANTHROPIC_API_KEY` 时可以 `lore auto` 无人值守归因；没有也能完整工作 —— **归因默认借用当前 harness 里的模型，零配置零 key**。

## 五条设计约束

| # | 约束 | 为什么 |
|---|---|---|
| 1 | **未命中零注入** | 不是注入"无相关知识"，是完全不动 |
| 2 | **单次 ≤300 token** | 注入过多就是污染上下文 |
| 3 | **fail-open** | 查询超时/失败/文件不存在一律放行，绝不阻塞编辑 |
| 4 | **人工确认闸** | 学到一条错规范的代价 >> 漏掉一条对规范 |
| 5 | **不改 agent 本身** | 只在工具调用边界介入 |

与 [agent-beacon](https://github.com/a1473838623/agent-beacon) 共享这套约束 —— 同一方法论的两个应用。

## 第三类知识：上下文状态

有些约束**写成提示词 agent 也遵循不了** —— 不是它不懂规则，是它**缺状态**。

典型例子：「不要扩大需求边界」。边界定义在需求层面、跨会话存在，而 agent 每次会话重置后
只看得到当前对话，于是把"边界"错解成"这次对话提到的范围"。
**规范说"不要越界"，状态说"界在这里"。缺了后者，前者是空话。**

```bash
lore spec set --id "REQ-118 支付回调幂等"               --scope "只改 PayCallbackService 的幂等判定"               --out "重构订单状态机;顺手升级依赖"
lore spec show / clear
```

活跃期间**每次编辑前无条件注入**，不参与相关性检索 —— 漏一次就可能越界。

由此知识库分三类，注入方式各不相同：

| 类别 | 例子 | 注入方式 | 为什么 |
|---|---|---|---|
| **常驻规范** | 用构造器注入 | CLAUDE.md，harness 每次加载 | 漏检即失效 |
| **上下文状态** | 当前需求边界 | 活跃期间**无条件**注入 | agent 缺的是状态不是规则 |
| **情境踩坑** | 这个文件的历史坑 | 按路径/符号检索 | 量大、偶尔相关 |

## 两条学习信号

学到规范的路径有两条，它们是正交的，缺一条就有系统性盲区。

**① 代码 diff。** agent 写文件 → 人改 → 比对 → 归因。这是主路径，
但它只看得见**结果**，看不见**要求**。

**② 对话里的批评。** 挂 `UserPromptSubmit` 钩子，把人说的批评本身存下来按类型聚合。

第二条不是补丁，是必需的：**有些规范从来不体现为一次 diff**。
"这段太长""这个词不专业""别写论述句"——人是在对话里说的，
说完 agent 自己去改，diff 里只有改完的样子，没有为什么要改。
只盯 diff 的话，同一类批评说十遍也学不到。

而且人愿意说第二遍，本身就是强信号：说明第一遍没被落实。
所以口头批评的阈值是 2 次，比代码规范的 3 次更低；
跨会话重复又比同一会话内重复更强——那说明不是一次沟通没说清，是真没学会。

```bash
lore critique          # 看反复出现的批评
```

聚类键取**批评类型**而非文本相似度。实测"这一段有点长"与
"冲突感知那段太长了"的文本相似度是 0，但它们显然是同一个抱怨——
批评句里被引用的具体内容是噪声，抱怨的类型才是信号。

检测用关键词而非模型判断：`UserPromptSubmit` 在人敲回车后同步执行，
加一次推理会让每次提问都卡一下。关键词不完美，但零延迟、可解释，
且误判的代价只是多一条候选，候选本来就要人工确认才入库。

## 看板的启动方式

```bash
lore dashboard            # 前台运行
lore dashboard -d         # 后台启动（推荐）
lore dashboard --status   # 查看状态
lore dashboard --stop     # 停止 · --restart 重启
```

后台启停对齐 [agent-beacon](https://github.com/a1473838623/agent-beacon) 的 `beacon start -d`。
**这是推荐路径** —— 看板是想看时才看的东西，不必常驻，也不必碰系统启动项。
停止时会**确认端口真的释放**再返回：只 kill 不确认的话，下次启动撞 EADDRINUSE，
而那个现象看起来像代码有问题。

### 开机自启（可选）

```bash
lore autostart on         # 启用 · off 关闭 · status 查看
```

在看板的「设置」里也能开关，同时可配自动更新与刷新间隔。

两个实现上的坑值得记：

**① Windows 不能往启动文件夹写脚本。**
实测 `.vbs` / `.cmd` / `.bat` / `.ps1` 全部 EPERM，而 `.txt` 可写 ——
这是 Defender 对启动项脚本的持久化防护，往那儿塞脚本正是恶意软件的经典手法。
`schtasks /SC ONLOGON` 也 Access denied（需提权）。
可行的是 **`.lnk` 快捷方式**：它不是脚本，也是正常软件的通行做法。

**② 必须固化仓库目录。**
看板是按仓库作用域的。从启动文件夹拉起时 `cwd` 是 Startup 目录，
`repoId` 会算成 `Startup`，看板显示一个不存在的仓库 ——
现象是「自启之后什么都没有」，很难查。所以启用时把当前仓库路径写进快捷方式的
工作目录与 `--cwd` 参数。

### 自动更新（可选）

启动时 `git pull --ff-only`。**只用快进**：本地有未提交改动或未推送提交时会停下来
交给你处理，不自动 merge —— 一个后台自启的工具偷偷把自己改坏，比不更新糟得多。
更新后当前进程加载的仍是旧代码，所以会明确提示**重启后才生效**。

`lore dashboard` → `http://127.0.0.1:4519`

显示：已确认规范 / 踩坑 / 候选进度 / 待归因 diff / 注入次数与 token 成本 /

## 语言约定

**注入进模型上下文的一切用英文；面向用户的输出跟随用户语言。**

| 内容 | 语言 | 为什么 |
|---|---|---|
| CLAUDE.md（含标题）、规范文本、踩坑文本、需求边界 | **英文** | 进模型上下文，token 更省、指令校准更好 |
| CLI 输出、看板、本文档、代码注释 | 跟随用户 | 给人看的 |

归因与 bootstrap 的提示词会显式要求模型**只用英文写 `rule` 字段**。

## 两个作用域

| 作用域 | 存哪 | 同步到 | 什么时候用 |
|---|---|---|---|
| **repo** | `convention/<repo>.md` | 项目 `CLAUDE.md` | 这个仓库特有的写法 |
| **global** | `convention/_global.md` | **用户级 `~/.claude/CLAUDE.md`** | 工具/环境级规范（Git 行为、PowerShell 编码、中文分词…） |

通用规范**每个会话都加载**，是真正持续在生效的那批。看板同时显示两个作用域并可筛选 ——
只显示本仓库的话，生效中的规范反而是隐形的。

```bash
lore sync            # repo → 项目 CLAUDE.md
lore sync --global --repo _global   # global → ~/.claude/CLAUDE.md
```

## 召回：关键词 vs 向量 vs 混合（有实测数据）

```bash
lore embed                        # 探测 embedding 后端
lore search "端口被占用怎么办"      # 自然语言检索知识库
lore eval compare                 # 三种模式跑同一份评测集
```

20 题人工标注集，symbol 与 natural 各 10 · 候选池 18 条 · recall@3 ·
embedding 用 Ollama 本地 `bge-m3`：

| 模式 | 总 recall | precision | top1 | **symbol** | **natural** |
|---|---|---|---|---|---|
| keyword | 50% | 17% | 50% | **100%** | **0%** |
| vector | 100% | 33% | 75% | 100% | 100% |
| **hybrid** | **100%** | **33%** | **85%** | **100%** | **100%** |

**结论不是"混合最好"，是"按查询形态选"**：

- **注入路径**的查询来自被编辑文件里的符号，属于 symbol 类 —— keyword 已经 100%，
  加向量是付 embedding 延迟换零收益。所以默认 keyword。
- **`lore search` 路径**的查询是自然语言 —— keyword 直接归零，必须走 hybrid。

两条路径默认值不同，这正是把指标**按查询类型分组统计**的价值：混在一起算总分会把结论抹平。

### 三个被数据推翻的判断

**① natural 只有 30%，起初以为是向量不行**

把同一批问题写成中英两版，对同一份英文语料检索：

| embedding 模型 | 中文提问 | 英文提问 | 差距 |
|---|---|---|---|
| `nomic-embed-text` | **30%** | 100% | 70 pt |
| `bge-m3` | **100%** | 100% | **0 pt** |

**瓶颈是跨语言，不是向量本身。** 两种归因的解法完全相反：若是向量不行，结论是弃用向量；
既然是跨语言，换多语言 embedding 就解决了。**先归因再动手，否则会改错方向。**

**② hybrid 第一版用 max 归一化后加权，被稀疏通道的噪声放大**

关键词通道天然稀疏，多数候选是 0 分。只要有一条拿到微弱匹配，哪怕原始分 0.05，
max 归一化后也变成 1.0，直接压过向量通道的真实高分。
改成 **RRF 倒数排名融合**后 top1 从 80% 提到 85% —— RRF 只看排名不看分值，
天然免疫量纲差异与稀疏噪声。

**③ CLI 参数解析只跳过旗标、没跳过旗标的值**

`lore search "xxx" --repo _global --k 3` 的实际查询变成了 `xxx _global 3`，
多出来的 token 污染 embedding，排序整个变样。
**现象很隐蔽 —— 看起来像召回算法不准，实际是入参就错了。**

> 评测集在 `~/.agent-lore/eval/<repo>.jsonl`，`lore eval init` 生成骨架。
> **query 刻意不自动生成** —— 用模型造题再用模型检索，等于自己给自己出题，数字没意义。

## 已知边界

- **归因准确率是天花板。** 人对文件的改动大部分是业务演进而非纠正 AI，噪声占多数。
  三道闸（置信度阈值、30 分钟采集窗、≥3 次累计）都是在压误报，代价是召回偏低。
- **同类归并是关键词级的**（ASCII 按词 + CJK 字符二元组），不是语义聚类。措辞差异过大时会漏并。
- **不自动判断"重复"还是"冲突"。** 实测：同义重复 0.64 ｜ 语义对立 0.36 / 0.54 ｜ 无关 0.00 ——
  相关与无关分得很开，但**重复与冲突的区间完全重叠**。字符串相似度只能判"是不是同一话题"，
  判不了"是不是对立"。所以只召回相关项，判断交给 `promote` 的人工确认闸。
- **绕过 hook 的文件修改会被误判为人类修正。** 用 `sed`/`python`/编辑器直接改文件不经过
  `PostToolUse`，检测逻辑（"未经上报的变更 = 人类修正"）就会把 agent 自己的改动算成修正。
  这是 L3 保底推断的固有代价：不依赖 harness 特性，就换不来精确的来源判定。
- **`lore stats` 在注入次数为 0 时不下结论** —— 必须能区分"规范没用"和"注入没生效"。
- 检索刻意不上向量：检索词天然是专有名词，关键词精确率更高。规模到千级再换，接口不变。

## 知识层

存储是文件，但文件之上有一层知识层。它**不引入任何新数据**，
只把已有数据里隐含的关系显式化：

```bash
lore knowledge          # 总览：生命周期 · 覆盖地图 · 关联密度
lore why <ruleKey>      # 单条规范的来源与证据
```

### 生命周期 —— 知识治理

一个知识库最大的问题不是存不下，是**存了一堆没人用、或者用了没效果的东西**，
而这两种都不会自己冒出来说话。所以给每条规范算一个状态：

| 状态 | 判据 | 意味着 |
|---|---|---|
| **疑似过时** | 入库 >14 天但**从未被注入** | 对应场景不再出现 |
| **疑似无效** | 注入过但**复发未减** | 规范本身无效，或表述不清 |
| 有效 | 注入后未再复发 | |
| 部分见效 | 复发减少但仍有发生 | |
| 新入库 / 候选中 | 尚无足够数据 | |

前两个在看板上**置顶**，因为它们是唯一需要你动手清理的。

### 覆盖地图 —— 空白比密集更有信息量

按技术域统计知识分布，并列出**一条知识都没有的域**。
某个域空白，要么那里没踩过坑，要么踩了没沉淀 —— 后者才是要补的。

### 知识关联 —— 是一堆经验还是一个体系

规范之间按话题相似度连边。**孤立点占多数说明还只是一堆互不相关的经验**，
连成簇才说明某个领域已成体系。当前 18 条规范 1 条边 16 个孤立点，
诚实地反映了它现在的状态。

### 溯源 —— 这条规则是怎么来的

`lore why <key>` 或在看板上点「溯源」，展开可见：
来源 diff、涉及文件、注入次数与 token、复发变化、相关规范。
**想删一条规范时，能看到它的全部证据再决定。**
